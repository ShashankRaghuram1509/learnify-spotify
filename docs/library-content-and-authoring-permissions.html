01

Overview — a two-layer permission model

The library's content is public to read but tightly governed to write. Every write is checked in up to two places: an application layer (UI gating and, for the Drive path, explicit role + ownership checks inside an Edge Function) and the database layer — PostgreSQL Row-Level Security (RLS) policies on the content tables plus policies on the Storage buckets. RLS is the real backstop: even if the UI is bypassed, the database rejects an unauthorized write.

Read model

The whole catalog — courses, modules, taxonomy, reviews — is world-readable (USING (true)). Only premium lesson bodies and private files (certificates) are gated.

Write model

Anchored on two facts: the caller's role (student/teacher/admin) and ownership (courses.teacher_id = auth.uid()). Teachers own their courses; admins override.

Source-of-truth caveat

A few live objects — the course_resources & course_materials tables and the course-materials bucket — exist in the running DB but not in the migrations, so part of the model lives outside version control (see §8).

How the library is laid out

The content hierarchy that makes up a course, with each level's read-visibility. PUBLIC world-readable · GATED conditional · PRIVATE owner-only.

courses PUBLIC READ
the hub · title, description, thumbnail_url, video_url, teacher_id, is_premium · one row per course
└─

└─
lessons GATED
the teachable units (video/text). Free-course lessons are public; premium-course lessons require enrollment.
course_resources PUBLIC
downloadable materials & links (pdf / video / link / document) shown by MaterialsList · ordered by position · defined outside migrations
course_materials PUBLIC
structured AI study content — overview, key_points, code_examples, practice_exercises (JSON) · defined outside migrations
reviews PUBLIC
student ratings & comments (write-gated to enrolled students)
categories · tags PUBLIC

The catalog is the library. Because courses, modules, taxonomy and resources are all world-readable, browsing/search works for anyone. The single access boundary inside a course is the premium-lesson gate: a premium course's lesson bodies are visible only to enrolled students, enforced directly in the lessons RLS policy — not just hidden in the UI.
03

Roles & how they are granted

Authoring rights flow entirely from a user's role. Roles live in their own table and are deliberately hard to self-assign.

The role model
  • Roles are app_role ∈ {student, teacher, admin}, stored in a dedicated user_roles table — separated from profiles for security
  • Checked via has_role(user, role) — a SECURITY DEFINER SQL function that reads user_roles, so RLS policies can call it without recursion
  • A user may hold multiple role rows (UNIQUE(user_id, role))
How you get a role
  • Signup → always student. The handle_new_user trigger forces the student role and ignores any client-supplied role in metadata (locked down after earlier versions trusted it)
  • Teacher / admin are provisioned by an admin — an RLS policy lets admins insert teacher role rows; the admin-create-instructor function does this server-side
  • Net effect: elevated authoring rights can't be self-granted
Design intent, verbatim from the migration: “Always assign 'student' role by default, ignoring any client input. Teachers and admins must be created through secure admin interface.” This is the linchpin of the authoring model — content-write power is bootstrapped only by an existing admin.

05

Course creation & editing flows

Two authoring surfaces write to the same courses table — one for teachers (self-service) and one for admins (full control).

Teacher — self-service

teacher/MyCourses.tsx

  • “Create Course” dialog → direct client insert into courses with teacher_id = self
  • Manages materials inline per course (upload + list)
  • Delete via client delete; edit button present but not yet wired
  • Governed by RLS: INSERT: has_role(uid,'teacher') and UPDATE/DELETE: uid = teacher_id AND has_role(uid,'teacher')

Admin — full management

admin/CourseManagement.tsx

  • Sees every course; can create, edit & delete any of them
  • Assigns a course to any teacher (sets teacher_id from a picker)
  • Uploads cover & video files to Storage (course-thumbnails, course-videos)
  • Governed by RLS: ALL: EXISTS(user_roles WHERE uid AND role='admin')
Modules & lessons are written only through the owning teacher's context — the RLS policy is ALL USING EXISTS(courses WHERE id = *.course_id AND teacher_id = auth.uid()). There is no admin policy on modules or lessons, so an admin editing another teacher's course cannot alter its module/lesson structure through the normal client (only courses-level fields).
06

Material & file upload architecture

Four buckets, and two distinct code paths for adding course materials — enforcing permission in different places.

Path A — Supabase Storage (in use)

MaterialsUpload.tsx uploads the file to bucket course-materials at path {courseId}/{timestamp}.{ext}, gets a public URL, then client-inserts a course_resources row. Permission rests on the Storage policy — the path's first segment must be a course the caller owns.

Path B — Google Drive (hardened)

upload-to-drive Edge Function does explicit checks in code — caller's user_roles.role === 'teacher' and courses.teacher_id === caller — then uploads to Google Drive and inserts the course_resources row pointing at the Drive link.

08

Findings, gaps & recommendations

Observations that matter for correctness and security of the authoring model, most notable first.

1 · Course creation isn't bound to the creator. The courses INSERT policy checks only has_role(auth.uid(),'teacher') — it never requires teacher_id = auth.uid(). Any teacher can create a course attributed to another teacher's id (and would then be unable to edit it, since UPDATE/DELETE require ownership). Fix: add WITH CHECK (teacher_id = auth.uid()) to the INSERT policy.
2 · Part of the model lives outside migrations. course_resources, course_materials and the course-materials bucket exist in the running database but have no CREATE/RLS statements in any migration. Their access rules can't be reviewed, diffed, or reproduced from source. Fix: capture them as migrations so the whole permission surface is in version control.
3 · Admins can't edit modules/lessons

“Admins can manage all courses” covers only the courses table. modules and lessons have owner-teacher-only policies and no admin clause, so an admin cannot restructure another teacher's curriculum via the client. Add admin clauses if that's intended.

4 · Two upload paths, uneven guarantees

The Storage path (MaterialsUpload) has no in-code ownership check and leans entirely on the bucket policy; the Drive path checks explicitly. Keeping both means two rule-sets to maintain. Consider standardising on one.

5 · Admin buckets have no path scoping

Thumbnail/video policies are role-only — any admin may write anywhere in those buckets. Low risk (trusted role), but a per-course path convention would tighten it.

6 · Role lookup uses .single()

Because user_roles allows multiple rows per user, the Drive function's .select('role')…​.single() would error for a user holding more than one role. Prefer has_role() or a .in() check.

Bottom line. The library is a public catalog with a single premium-lesson gate, and authoring is a clean role + ownership model: students can't write, teachers own their courses and materials, admins override at the course level, and system-only records (enrollments, certificates) are sealed off from direct writes. The main hardening opportunities are binding course creation to its owner, and bringing the out-of-migration objects back under version control.
